# Contributing to Laraplate

Thank you for your interest in Laraplate. This guide applies to every public repository of the
Laraplate ecosystem:

| Repository | What it is | License |
|---|---|---|
| [laraplate](https://github.com/getlaraplate/laraplate) | Laravel backend and Filament admin | AGPL-3.0 |
| laracore, laracms, laraai, laraerp, larames, larasao, larashop, laracrm | Backend modules (`Modules/*` of `laraplate`) | AGPL-3.0 |
| [laraedge](https://github.com/getlaraplate/laraedge) | Go edge agent for machine data | AGPL-3.0 |
| [whisper-api](https://github.com/getlaraplate/whisper-api), [sentence-transformers-api](https://github.com/getlaraplate/sentence-transformers-api) | Python inference services | Apache-2.0 |

Please also read our [Code of Conduct](CODE_OF_CONDUCT.md). To report a security issue, do not
open a public issue: write to myentity@inwind.it.

## Our licensing commitment

Laraplate is **dual licensed**: the **AGPL-3.0 edition** is free for everyone, and a **commercial
license** is available to organisations that cannot accept the AGPL obligations. The two are the
same software under different terms. We commit that:

1. **The AGPL edition is the project.** Every release is published under the AGPL at the same time
   and with the same code as any commercial release. There are no commercial-only features in the
   AGPL projects, and no delayed open source releases.
2. **Development happens in the open**, in these public repositories, for the community and with
   its help: issues, discussions and pull requests are where Laraplate moves forward.
3. **Your contributions stay open.** Code you contribute is always available under the AGPL. The
   contributor agreement lets us offer it under a commercial license as well, never instead.
4. **The commitment outlives us.** It will be written into our Contributor License Agreement, which
   we are finalising, and bind anyone who takes over the project.

Work done for a specific customer under a separate agreement, such as custom modules or private
modifications, is not part of these projects and is not covered by this commitment. What belongs in
the public projects is never kept out of them by being delivered to a customer instead.

`laraedge` is the open, generic connector for machine data. The Laraplate UI applications, the
vendor-specific machine connectors (plugins built on the Apache-2.0 plugin SDK of the edge agent) and
the data importers are separate proprietary products, built and distributed from their own
repositories. They are not part of the AGPL projects listed above: the UI talks to the backend over
its HTTP API, and plugins and importers use only the public interfaces and extension points of the
AGPL projects, which are themselves open. Nothing that belongs in the AGPL projects is moved into
them.

## Before you start

- **Bugs:** search the existing issues first, then open one with the bug report template.
  Include versions, steps to reproduce, and what you expected.
- **Features and larger changes:** open an issue to discuss the idea before writing code.
  Laraplate has an opinionated architecture, and agreeing on the design first saves you from
  writing a pull request that cannot be merged.
- **Small fixes** (typos, docs, obvious one-line bugs) can go straight to a pull request.

## Contributor License Agreement

To keep dual licensing possible (see [our licensing commitment](#our-licensing-commitment)), external
code contributions will be accepted under a Contributor License Agreement. **We are finalising it
and it is not published yet, so we cannot merge external pull requests for now.** Bug reports,
discussions, documentation feedback and design proposals are welcome in the meantime.

If you are interested in contributing code, or in a contribution agreement for your organisation,
write to myentity@inwind.it.

## AI-assisted contributions

You are welcome to use AI tools. You stay responsible for what you submit:

- Review, test and understand every change before you open the pull request. Write the description
  yourself, in your own words.
- Make sure you are allowed to submit it: the tool's terms must let you license its output, and it
  must not reproduce third-party code you cannot license. Our contributor agreement will ask you to confirm this.
- Large or complex changes written mostly by a tool, without careful human review, will not be
  accepted. Mass-opened issues or pull requests generated by a tool are closed without review.

We may ask whether AI tools were used and how.

## Development workflow

1. Fork the repository and create a branch from the default branch (`master` or `main`).
2. Make focused changes: one topic per pull request.
3. Add or update tests for every behaviour change.
4. Update the documentation affected by your change (see below).
5. Run the checks for the repository you are working in.
6. Open a pull request and fill in the template.

### Commit messages

We use [Conventional Commits](https://www.conventionalcommits.org/), because the changelogs are
generated from them:

```
feat(cms): add scheduled publishing to contents
fix(core): keep the owner's updated_at when restoring a version
docs(erp): document the invoice numbering settings
```

Common types: `feat`, `fix`, `docs`, `refactor`, `test`, `perf`, `chore`. Use the module or area
as the scope when it helps. Write the subject in English, in the imperative mood.

### Language

Code, comments, PHPDoc, commit messages and documentation are written in English.

## Repository-specific checks

### Laravel backend and modules (`laraplate`, `laraplate-*` modules)

- PHP 8.5, Laravel 12, Filament 5, Livewire 4. Read the module `README.md` before working in a
  module.
- Every PHP file declares `declare(strict_types=1);`, with explicit parameter and return types.
- Follow the existing structure and the style of sibling files. Do not add new dependencies
  without discussing them in an issue first.
- Tests use Pest and live in the module's own `tests/` folder for module work.
- Module changes belong in the module repository. In `laraplate`, a module is a git submodule
  under `Modules/`.

Before opening the pull request, run at least:

```bash
composer test:lint
composer test:types
php artisan test --compact
```

`composer test` runs the full suite, including type coverage, 100% code coverage and license
checks. CI runs the test suite on every pull request.

Shipped behaviour must be documented in the module's `docs/` folder, and new or changed
environment variables in the module `README.md`.

### Edge agent (`laraedge`)

```bash
go vet ./...
go test -race ./...
```

`laraedge` talks to Laraplate only through its published protocol and configuration
routes. Proprietary drivers and profiles are not accepted into this repository: build them as
plugins on the Apache-2.0 plugin SDK instead.

### Python services (`whisper-api`, `sentence-transformers-api`)

Keep the services small and dependency-light. Describe in the pull request how you tested the
change, including the model and hardware you used.

## Pull request review

- A maintainer will review your pull request as soon as possible. This is a small project, so
  please be patient.
- CI must pass before a pull request can be merged.
- We may ask for changes, or close pull requests that do not fit the project's direction. When we
  do, we will explain why.

For questions about using Laraplate, write to myentity@inwind.it or open an issue in the repository concerned.
